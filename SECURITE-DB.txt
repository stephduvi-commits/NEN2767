SÉCURITÉ BASE DE DONNÉES (Supabase) — NOTES DE DÉCISION
=========================================================
Projet Supabase : NEN2767 (jingwuxekcihiiktsidy)
Dernière mise à jour : 2026-08-08

Ce fichier documente les correctifs de sécurité appliqués à la base et,
surtout, les cas où un avertissement automatique (lint Supabase) a été
volontairement IGNORÉ car son correctif par défaut aurait cassé l'app.
À consulter avant d'appliquer aveuglément un correctif suggéré par un lint
de sécurité sur ce projet.


1. FONCTIONS is_admin() ET is_contributor()
--------------------------------------------
Définition (schéma public) :

  CREATE FUNCTION public.is_admin() RETURNS boolean
    LANGUAGE sql SECURITY DEFINER STABLE SET search_path = public AS $$
    SELECT EXISTS (SELECT 1 FROM public.profiles WHERE id = auth.uid() AND role = 'admin');
  $$;

  (is_contributor() est identique, avec role IN ('admin','contributeur'))

Rôle : vérifient uniquement si L'UTILISATEUR APPELANT LUI-MÊME (via
auth.uid(), pas un paramètre) a le rôle admin/contributeur dans la table
profiles. Ne renvoient qu'un booléen, ne prennent aucun paramètre, ne
peuvent donc jamais faire fuiter d'information sur un autre utilisateur.

Utilisées à l'intérieur des policies RLS suivantes :
  - public.action        : contributor_insert_action, contributor_update_action,
                            contributor_delete_action
  - public.profiles      : admin_update_profiles, admin_delete_profiles

  storage.objects N'UTILISE PLUS is_contributor() depuis le 2026-08-08 —
  voir section 4 (bug de propagation JWT côté Storage).

Pourquoi SECURITY DEFINER (et pas SECURITY INVOKER) :
  La fonction lit la table profiles. Si elle était en SECURITY INVOKER,
  cette lecture interne serait elle-même soumise aux policies RLS de
  l'appelant — risque de récursion / dépendance circulaire quand la
  fonction est appelée depuis une policy définie SUR profiles elle-même
  (admin_update_profiles, admin_delete_profiles). SECURITY DEFINER est le
  pattern officiellement recommandé par Supabase pour ce type de fonction
  utilitaire de rôle, précisément pour éviter ce problème.

Droits d'exécution (EXECUTE) — état voulu et vérifié :
  - anon           : AUCUN accès (révoqué explicitement, y compris le
                      grant par défaut que Supabase accorde à la création
                      de toute fonction — PUBLIC seul ne suffit pas à le
                      retirer, il faut aussi "REVOKE ... FROM anon").
  - authenticated   : accès NÉCESSAIRE — c'est ce rôle qui évalue les
                      policies RLS ci-dessus pour tout utilisateur connecté
                      (admin, contributeur ET client). Le lui retirer
                      bloque l'ajout/modif/suppression d'actions et la
                      gestion des utilisateurs pour TOUT LE MONDE, y
                      compris les admins légitimes.
  - service_role    : accès conservé (par défaut Supabase, sans impact).

search_path : explicitement fixé à "public" dans la définition de la
fonction (SET search_path = public). C'est la protection standard contre
le détournement d'une fonction SECURITY DEFINER (empêche qu'une table/
fonction malveillante placée dans un autre schéma soit résolue à la place
de la bonne à l'intérieur de la fonction).


2. LINT "SECURITY DEFINER appelable par authenticated" — À IGNORER ICI
------------------------------------------------------------------------
Les scanners de sécurité automatiques (ex. Supabase Advisor / lints du
type 0025_public_bucket_allows_listing, function_search_path_mutable,
etc.) signalent parfois is_admin()/is_contributor() comme "SECURITY
DEFINER appelable par authenticated via /rest/v1/rpc/..." et suggèrent
par défaut l'une de ces trois options :

  Option 1 : REVOKE EXECUTE ... FROM authenticated, public;
     -> NE PAS APPLIQUER. Casse l'app (voir ci-dessus : authenticated a
        besoin de cet accès pour que les policies RLS fonctionnent).

  Option 2 : ALTER FUNCTION ... SECURITY INVOKER;
     -> NE PAS APPLIQUER. Réintroduit le risque de récursion RLS que
        SECURITY DEFINER a été choisi pour éviter (voir section 1).

  Option 3 : garder SECURITY DEFINER, s'assurer que la fonction ne fait
             que renvoyer un booléen sans fuite d'info, avec search_path
             pinné.
     -> C'EST LA SITUATION ACTUELLE. Rien à changer.

Conclusion : si ce lint réapparaît (il peut revenir tant que la base a
des fonctions SECURITY DEFINER appelables par authenticated — c'est
inhérent au pattern, pas un vrai problème), vérifier juste que :
  a) la fonction ne renvoie toujours qu'un booléen basé sur auth.uid(),
  b) anon n'a toujours pas EXECUTE,
  c) search_path reste pinné,
  puis considérer le lint comme un faux positif et ne rien changer.


3. AUTRES CORRECTIFS DE SÉCURITÉ APPLIQUÉS CETTE SESSION
-----------------------------------------------------------
- Colonne action.id_action élargie de varchar(10) à varchar(20)
  (corrige un blocage d'ajout d'action, sans lien sécurité).

- RLS "USING (true)" trop permissives supprimées sur :
    public.action    : public_delete_action, public_update_action
    public.profiles  : public_all_profiles
  (permettaient à n'importe qui, même non connecté, de supprimer/modifier
  des actions ou des profils utilisateurs directement via l'API).

- RLS profiles.DELETE : policy authenticated rétablie après la
  suppression ci-dessus (auth_delete_profiles), pour ne pas casser la
  fonctionnalité de suppression d'utilisateur du panneau admin — puis
  remplacée par une version admin_delete_profiles restreinte au rôle
  admin (voir point suivant).

- Passage d'un modèle "connecté = tous droits" à un modèle par rôle :
    public.action   : lecture = tout connecté, écriture = admin/contributeur
    public.profiles : modification/suppression = admin uniquement
  (correspond exactement à isContrib()/isAdmin() déjà utilisés côté app —
  c'est maintenant appliqué aussi côté base, pas seulement dans l'UI).

- storage.objects (bucket action-photos, public) :
    - Policies SELECT larges supprimées (permettaient le listing/
      énumération des fichiers du bucket via l'API Storage — lecture par
      URL directe non affectée, un bucket public n'a pas besoin de policy
      SELECT pour ça). CORRECTIF : cette affirmation était incomplète —
      voir section 4, retirer le SELECT a cassé l'UPLOAD (pas la lecture).
      Un SELECT a dû être réintroduit.
    - Policies INSERT/DELETE en doublon, non protégées malgré leur nom
      ("authenticated upload/delete photos" ne vérifiait en réalité aucune
      authentification) remplacées par des policies réservées aux
      admins/contributeurs (is_contributor()). VOIR SECTION 4 : ce
      changement a cassé l'upload de photos et a été corrigé le 2026-08-08.

- Recommandation en attente (à faire manuellement, hors DB) : activer
  "Leaked Password Protection" dans Supabase Dashboard > Authentication >
  Password Security, pour vérifier les mots de passe contre HaveIBeenPwned
  à la création/changement de compte.


4. BUG (2026-08-04 → 2026-08-08) : upload de photos cassé sur
   storage.objects — CAUSE JAMAIS CONFIRMÉE, NE PAS RÉINTRODUIRE
   is_contributor() SUR storage.objects SANS TEST RÉEL PRÉALABLE
------------------------------------------------------------------------
Symptôme : depuis le passage des policies storage.objects (bucket
action-photos) à is_contributor() le 2026-08-04, TOUT upload de photo
(mobile et PC, comptes admin ET contributeur) échouait avec un 400 et
l'erreur Postgres "new row violates row-level security policy for table
objects" — y compris pour des admins actifs venant de se connecter
(token JWT valide et non expiré, vérifié via les logs auth).

État final (résolu le 2026-08-08) — policy actuellement en place :

    CREATE POLICY "action_photos_all" ON storage.objects
    FOR ALL
    USING (bucket_id = 'action-photos')
    WITH CHECK (bucket_id = 'action-photos');

Aucune vérification de rôle (admin/contributeur) ni d'authentification
réelle : équivalent au comportement bugué d'avant le 4 août (n'importe
qui connu du bucket peut lire/écrire/supprimer). Accepté comme
compromis temporaire — voir "limite acceptée" plus bas.

Ce qui a été essayé et a ÉCHOUÉ, dans l'ordre (toutes ces tentatives
produisaient exactement la même erreur RLS, y compris la dernière qui
est pourtant la policy la plus permissive imaginable avant l'état final) :
  1. is_contributor() avec roles={public} (version du 4 août).
  2. TO authenticated WITH CHECK (bucket_id = '...') sans fonction.
  3. Retour à is_contributor() + ajout d'une policy UPDATE manquante
     (hypothèse : le header x-upsert de Storage déclenche un
     INSERT ... ON CONFLICT DO UPDATE, qui exigerait une policy UPDATE
     même sans conflit réel — index unique sur (bucket_id, name)).
  4. GRANT EXECUTE sur is_contributor()/is_admin() à supabase_storage_admin
     (rôle réellement utilisé par le service Storage, découvert via un
     trigger de diagnostic — PAS "postgres" ni "authenticated").
  5. Policy triviale bucket_id = 'action-photos' SANS aucune fonction ni
     restriction de rôle — ÉCHOUE ENCORE, alors qu'un trigger de
     diagnostic (BEFORE INSERT, RAISE WARNING) confirmait dans la MÊME
     transaction, 1ms avant l'échec, que auth.uid()/is_contributor()
     étaient corrects.

Ce qui a réellement débloqué la situation : suppression MANUELLE de
TOUTES les policies storage.objects via le Dashboard Supabase (Storage
> Policies), suivie de la recréation d'UNE SEULE policy propre
("action_photos_all" ci-dessus, FOR ALL) via SQL.

CAUSE RACINE identifiée après coup (toujours le 2026-08-08) : la policy
FOR ALL a ensuite été volontairement splittée en 3 policies séparées
(INSERT/UPDATE/DELETE, sans SELECT — pour répondre à l'avertissement
Supabase Advisor "Clients can list all files in this bucket"). Résultat
immédiat : l'upload recasse EXACTEMENT comme avant, avec la même erreur.
En remettant FOR ALL (qui inclut implicitement SELECT), ça refonctionne.
Conclusion : contrairement à ce qu'indiquent la doc Supabase et l'Advisor
("un bucket public n'a pas besoin de policy SELECT, la lecture par URL
directe la contourne"), le service Storage a ICI besoin d'une policy
SELECT sur storage.objects pour que l'upload/upsert fonctionne — très
probablement une vérification interne d'existence du fichier (le header
x-upsert envoyé par l'app déclenche ce chemin). C'est cette policy
SELECT manquante (retirée le 4 août, jamais rétablie depuis) qui a été
la cause racine de tout l'incident du 4 au 8 août, et pas is_contributor()
ni aucune des hypothèses de rôle/JWT explorées avant — celles-ci
échouaient toutes pour la même raison sous-jacente (absence de SELECT),
ce qui a rendu le diagnostic très trompeur.

Limite acceptée : n'importe quel utilisateur connecté OU NON (la policy
ne vérifie même plus auth.role()) peut lire la LISTE des fichiers
(SELECT), uploader/modifier/supprimer des photos dans ce bucket — c'est
exactement ce que l'Advisor Supabase signale ("Clients can list all
files in this bucket"). Sans impact fonctionnel grave actuel : les 5
comptes existants sont tous admin ou contributeur, et le contenu du
bucket (photos d'observations de bâtiments) n'est pas hautement
sensible. Mais c'est une régression de sécurité volontaire, gardée
UNIQUEMENT parce que retirer le SELECT casse l'upload (voir plus haut).

À FAIRE avant de resserrer à nouveau cette policy (ex. remettre
is_contributor(), ou séparer à nouveau SELECT des autres commandes) :
  a) Ne JAMAIS se fier à un test SQL direct (via l'éditeur SQL / MCP)
     pour valider une policy storage.objects — il ne reproduit PAS
     fidèlement le contexte du service Storage (rôle réel de connexion
     = supabase_storage_admin, pas postgres/authenticated). Tester
     uniquement avec un vrai upload depuis l'app.
  b) GARDER une policy SELECT sur storage.objects pour ce bucket, même
     en resserrant les autres commandes — c'est elle qui manquait et qui
     a causé tout l'incident (voir plus haut). Un SELECT restreint à
     `TO authenticated` (au lieu de public) réduirait déjà l'exposition
     sans revenir au bug : à tester en conditions réelles avant d'adopter.
  c) Si un resserrement recasse l'upload, supprimer TOUTES les policies
     du bucket via le Dashboard (pas juste DROP POLICY en SQL) avant de
     recréer, au cas où l'état orphelin en soit la cause.
  d) Envisager de contacter le support Supabase pour confirmer/comprendre
     pourquoi Storage a besoin d'un SELECT ici alors que leur propre doc
     dit le contraire pour les buckets publics (un rapport détaillé avait
     été préparé le 2026-08-08).
